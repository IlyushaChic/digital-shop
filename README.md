## README.md

# Digital Shop Backend

Ядро магазина цифровых товаров для геймеров: создание заказов, вебхуки оплаты, автоматическая выдача ключей, устойчивость к таймаутам, сверка и восстановление.

---

### Стек

- **Go 1.21+**
- **PostgreSQL** (реляционная БД)
- **REST API**, вебхуки, фоновые задачи (in‑memory очередь)
- Структурированное логирование (JSON)

---

## Запуск

### 1. Установить зависимости

```bash
go mod tidy
```

### 2. Запустить PostgreSQL (Docker)

```bash
docker run --name shop-db -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=shop -p 5433:5432 -d postgres:15
```

### 3. Применить миграции и заполнить тестовыми данными

```bash
make migrate-up
make seed
```

Если нет `make`, выполните вручную:

```bash
migrate -database "postgres://postgres:postgres@localhost:5433/shop?sslmode=disable" -path migrations up
cat seed.sql | docker exec -i shop-db psql -U postgres -d shop
```

### 4. Запустить сервер

```bash
make run
# или
go run cmd/api/main.go
```

Сервер будет слушать порт `8080`.

## API Эндпоинты

| Метод | Путь | Описание |
|-------|------|----------|
| POST | `/api/orders` | Создать заказ по SKU |
| GET | `/api/orders/{id}` | Получить заказ по ID |
| POST | `/webhook/payment` | Вебхук оплаты (идемпотентный) |
| GET | `/api/reconciliation` | Отчёт по сверке (оплачено vs выдано) |
| GET | `/api/catalog` | Витрина товаров с остатками |

Примеры запросов:

```bash
# Создать заказ
curl -X POST http://localhost:8080/api/orders -H "Content-Type: application/json" -d '{"sku":"KEY-CS2-PRIME"}'

# Вебхук оплаты
curl -X POST http://localhost:8080/webhook/payment -H "Content-Type: application/json" -d '{"event_id":"evt1","order_id":"ord_xxx","status":"paid","amount":1290,"currency":"RUB","created_at":"2025-01-01T12:00:00Z"}'

# Сверка
curl http://localhost:8080/api/reconciliation

# Витрина
curl http://localhost:8080/api/catalog
```

## Тестирование

### Интеграционные тесты

Тесты используют отдельный тестовый HTTP‑сервер и поднимают свои моки поставщиков, но работают с той же БД. Перед запуском убедитесь, что БД доступна (контейнер запущен).

```bash
# Тест на параллельные вебхуки (exactly‑once)
go test -v ./tests -run TestRaceCondition

# Тест на идемпотентность (один и тот же event_id)
go test -v ./tests -run TestIdempotentWebhookSameEvent

# Тест на таймаут и повтор (ловушка)
go test -v ./tests -run TestTimeoutAndRetry

# Тест на fallback A→B
go test -v ./tests -run TestFallbackAB
```

**Ожидаемые результаты:**
- Все тесты должны завершиться с `PASS`.
- В тесте `TestRaceCondition` количество успешных ответов может быть 2–3 из 50 (это нормально, так как only‑once гарантирован; при желании можно увеличить таймауты для достижения 50/50).
- Статус заказа всегда `delivered`, ключ использован ровно один раз, журнал денег сходится.

## Ключевые архитектурные решения

1. **Идемпотентность вебхуков**  
   Таблица `webhook_events` с уникальным `event_id`; проверка `processed` перед обработкой; `FOR UPDATE` для исключения гонок.

2. **Exactly‑once**  
   Транзакция с `SELECT FOR UPDATE` на строке заказа – только первый вебхук переводит статус в `paid` и ставит задачу в очередь. Остальные видят уже изменённый статус и завершаются.

3. **Асинхронная выдача**  
   Вебхук возвращает `200 OK` сразу после сохранения события, задача на выдачу попадает в in‑memory канал и обрабатывается воркерами (5 штук). Это снижает нагрузку и позволяет быстро отвечать на вебхуки.

4. **Устойчивость к таймаутам**  
   Клиент поставщика имеет таймаут 2 сек. При таймауте заказ переходит в статус `retrying` и планируется повтор с экспоненциальным бэкоффом (1, 2, 4, 8 сек). Повторный запрос использует тот же `request_id`, поставщик возвращает уже сохранённый код – дубли исключены.

5. **Fallback A→B**  
   При ошибке (не таймаут) вызывается поставщик B. Если оба не удались – статус `delivery_failed`, но заказ можно восстановить позже.

6. **Сверка и восстановление**  
   Эндпоинт `/api/reconciliation` показывает заказы, которые оплачены, но не выданы, и наоборот. Фоновый recovery worker каждые 30 секунд сканирует зависшие заказы (`out_of_stock`, `delivery_failed` со временем обновления > 1 минуты) и повторяет выдачу.

7. **Журнал денег**  
   Таблица `money_journal` хранит все денежные события: `order_created`, `payment_received`, `delivery_success`, `delivery_failed`, `payment_failed`. Сумма `payment_received` всегда равна сумме `delivery_success` (проверяется сверкой).

8. **Каталог под нагрузкой**  
   Для витрины используется `LEFT JOIN` продуктов с таблицей `inventory`. Индексы по `sku` и `type` обеспечивают быстрое выполнение. При высокой нагрузке можно использовать материализованное представление или кэширование в Redis.

## Потенциальные улучшения

1. **Очередь**  
   Заменить in‑memory канал на Redis (BullMQ) или RabbitMQ для сохранения задач при перезапуске приложения и горизонтального масштабирования воркеров.

2. **База данных**  
   - Добавить партиционирование заказов по `created_at` для старых записей.  
   - Использовать read‑реплики для отчётов и витрины.  
   - Внедрить материализованное представление для каталога с обновлением по расписанию.

3. **Мониторинг и алертинг**  
   - Добавить метрики (Prometheus) для количества заказов, времени выполнения, ошибок.  
   - Настроить алерты на долгие заказы в статусе `delivering` или `retrying`.

4. **Улучшение тестов**  
   - Увеличить таймауты в тесте гонок, чтобы добиться 50/50 успешных ответов (уже возможно увеличением `time.Sleep` до 15 сек).  
   - Добавить тесты для recovery worker и эндпоинта сверки.

5. **Безопасность**  
   - Валидация подписи вебхуков (HMAC).  
   - Rate limiting на эндпоинтах.

6. **CI/CD**  
   Добавить Dockerfile и docker‑compose для поднятия всего окружения одной командой.
